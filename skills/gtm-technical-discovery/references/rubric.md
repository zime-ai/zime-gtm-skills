# Technical discovery rubric

Seven dimensions for whether a technical evaluation or POC is set up to
succeed, rather than scoped on hope.

## 1. Current technical environment mapped

What's actually in place today — systems, integrations, data sources — that
any solution would need to work alongside? A POC scoped without this is
guessing.

## 2. Future-state vision

Does the prospect have a specific picture of what "working" looks like
technically, or only a vague sense that things should be better?

## 3. POC scope clarity

If a POC is being discussed, is there a specific, bounded scope — what's
being tested, over what period, against what data — or is it still an
open-ended "let's try it out"?

## 4. Technical stakeholders identified

Are the people who'll actually evaluate this technically (architects, IT,
security, data owners) named and looped in, or is this still only a
conversation with a business buyer?

## 5. Success metrics for the evaluation

Is there an agreed, specific bar for what counts as a successful technical
evaluation, defined before it starts rather than argued about after?

## 6. Resourcing for the evaluation

Does the prospect have the internal time and access needed to actually run
a POC — someone to provide test data, configure access, show up to check-
ins — or is this likely to stall on their side?

## 7. Clear next technical step

Did the call end with a specific next step — a sandbox, a scoping document,
a scheduled kickoff — or just a general "sounds interesting"?

## Reads-well-too check

Sanity-check against a call you know led to a well-scoped, successful POC.
If it still comes back mostly Missed, loosen the read before reporting.
